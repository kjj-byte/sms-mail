## 必须修复

### 1. SMS-Man 返回其他国家的数据时，仍发布为请求国家

- **位置**：`public_smsman.go:109`、`public_smsman.go:137`、`public_smsman.go:152`。
- **业务与问题**：采集器根据请求国家给价格打标签，响应中的 `country_id`、`country` 没有进入解码结构，也没有核对 `application_id` 与服务映射键。上游如果返回错误国家或缓存串线，本站会把报价归到错误国家，并将请求国家重新写入所谓证据。
- **已验证**：隔离响应中请求国家为美国，实际响应为 `country_id=44, country=United Kingdom`；结果发布为“美国 USD 0.01”，证据还被改写为 `country_id=1`。这证明校验缺口，不表示已证明线上目录存在错价。
- **最小方案**：解码并核对响应国家 ID、应用 ID；不一致时拒绝对应结果、记为部分失败、保留旧价格。证据保留实际响应字段。复用 OnlineSIM 已有的“返回国家必须等于请求国家”原则。
- **不修影响**：用户按国家比价得到不适用的价格；后续只比较金额和证据会漏掉这种错误。
- **验收**：增加正确国家、错误国家、错误应用 ID、缺失必需 ID 的回归；错误响应不得生成该国家的新报价，不得刷新旧报价核验时间。

### 2. 静态页面的过期提示固定在生成时，之后不会自动过期

- **位置**：`generate.go:282`、`generate.go:348`；`web/app.js:100`、`web/app.js:114`。
- **业务与问题**：后端在生成时计算 `Stale`，前端只读取布尔值 `w`。某次采集后如果持续更新失败，哪怕用户隔多天重新打开页面，也不会根据现有日期显示待更新。
- **已验证**：当前产物的 28776 条展示记录全部没有 `w=true`。将浏览器时间推进 9 天后，28737 条有采集时间的展示行均超过 24 小时，仍没有过期提示。
- **最小方案**：前端初始化时，根据已有的报价采集时间、报价核验日、产品核验日重新计算过期状态，并保留后端已有的过期标志。按原有“自动价格 24 小时、人工资料 7 天”规则，不新增在线依赖；日期边界应明确使用的时区。
- **不修影响**：历史价格看起来仍在维护期内，削弱“报价待更新”这一关键业务提示。
- **验收**：覆盖 24 小时前后、7 天前后、页面生成后隔日访问；如支持长期打开页面，再加定时刷新或恢复可见时重算。

### 3. 更新价格与生成导航的互斥检查有时间窗口

- **位置**：`admin-panel/main.go:202`、`admin-panel/main.go:206`、`admin-panel/main.go:261`、`admin-panel/main.go:264`。
- **业务与问题**：生成导航先检查 `pricing`，之后才获得 `building` 锁；价格任务则只短暂试拿 `building`，马上释放，再设置 `pricing`。检查和实际占用没有组成一次原子操作。
- **代码路径已确认，未做并发时序动态复现**：生成请求先读到“没有采集”；价格请求检查并释放生成锁，启动采集；生成请求随后也能拿到生成锁。两个原本要求互斥的任务即可同时执行。发布文件锁只能在实际发布阶段阻止碰撞，不能修复整个任务的互斥承诺。
- **最小方案**：让两个任务在开始时试拿同一把任务锁，并持有到任务结束；后台采集在 goroutine 结束时释放。`priceMu` 继续只保护界面状态。
- **不修影响**：双标签操作或临近同时点击可能让生成读取到旧目录，或导致一个任务因发布锁失败；界面宣称的任务状态与实际结果可能不符。
- **验收**：用阻塞的假生成器/采集器固定执行时序；一个任务运行时，另一个入口必须返回冲突；覆盖成功和失败后锁都释放。

## 应该修复

### 4. 最后一个来源采集中取消，仍会保存目录

- **位置**：`prices.go:438`、`prices.go:477`、`prices.go:498`、`prices.go:504`。
- **业务与问题**：取消检查只在每个来源开始时执行。若取消发生在最后一个来源内部，循环结束后仍会写备份、替换 catalog，并返回 `Saved=true`。CLI 随后还会尝试生成页面。
- **已验证**：临时 catalog 中只配置一个来源，在模拟 HTTP 请求时取消 context；最终返回错误，但 catalog 内容发生变化，且 `Saved=true`。没有发现价格金额被清空，问题是取消后仍提交状态/数据。
- **最小方案**：在完成采集后及开始正式提交前再检查用户取消状态。区分用户取消与“25 分钟预算耗尽后保存已有有效结果”的策略，不把两者简单混成一种失败。
- **不修影响**：Ctrl+C 不能可靠保证未提交；用户可能以为操作已取消，实际目录或页面已发生变化。
- **验收**：取消最后来源、取消非最后来源、预算耗尽三个测试分别断言明确的保存策略；用户取消时正式 catalog 的字节应保持原样。

### 5. 目录保存后生成失败，界面却承诺“旧价格保留”

- **位置**：`cmd/priceupdate/main.go:72`、`cmd/priceupdate/main.go:74`；`admin-panel/main.go:283`、`admin-panel/main.go:285`。
- **业务与问题**：流程先提交新 catalog，再生成 dist。若输出目录不允许覆盖、邀请配置失效或发布失败，新 catalog 已存在、旧页面仍在；管理端将所有非零退出统一显示为“旧价格与上版页面保留”。
- **已验证**：在临时目录完成有效价格采集，再用含 `keep.txt` 的输出目录触发生成拒绝；生成失败后 catalog 仍保持刚提交的新内容。这种分阶段状态本身可以接受，但当前提示不准确，也缺少明确恢复入口。
- **最小方案**：先把结果区分为“采集未提交”“目录已更新、页面生成失败”“全部完成”；管理端显示真实状态并提示单独重生成导航。无需为了这个问题引入跨文件事务或自动回滚新价格。
- **不修影响**：管理员无法判断该重新采集还是只需重新生成，页面、目录及界面采集时间可能互不一致。
- **验收**：覆盖采集成功但生成失败、全来源失败却已保存失败状态、成功重生成旧目录三种情况，断言提示与实际文件一致。

## 实施顺序与改动范围

1. 先修 1、2：直接影响按国家比价与价格新鲜度。改采集器、前端及对应测试；前端资源嵌入二进制，修复后必须重建 sitegen 并重新生成 dist。
2. 再修 3、4：改本机任务入口与采集提交边界，补固定时序和取消回归；不增加依赖。
3. 最后修 5：改更新器结果传递、管理端提示及测试，并同步 README 的失败行为说明。

所有修复均应保持“只读采集、跳转平台官网”的业务边界，不加入支付、代购或额外账户系统。
